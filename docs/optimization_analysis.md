## Linear Conflict 的实现与验证

实现位于 `PuzzleBoard.linearConflict`。对每个目标行，取当前已在该目标行的将牌，按出现顺序写出它们的目标列。能保持相对顺序的最长递增子序列可以留在行内；至少有“序列长度减 LIS 长度”枚将牌必须离行再回来，每枚贡献 2 步额外代价。列同理。本实现没有把互相共享将牌的所有冲突对直接相加。

一致性的局部理由是：沿行移动不会改变行内非空将牌的相对顺序；跨行时只会在一条相关目标行的序列中增删一个元素，最少离行数至多改变 1。若移出已在目标行的将牌导致冲突项减少 2，其 Manhattan 反而增加 1，合计下降至多 1；列的分析相同。距离与序列全部使用输入目标的位置索引，因此不依赖标准目标排列。

新增 [PuzzleOptimizationTest](../tests/PuzzleOptimizationTest.java) 使用独立的 64 位棋盘编码和相邻交换 BFS，不调用生产代码的 `actions/next` 计算精确距离。三个不同目标各枚举 181,440 个可达 8-Puzzle 状态，检查目标零值、Manhattan 下界、精确距离上界及每条合法有向边的一致性；同时把生产后继集合与独立集合逐状态比较。两个 4×4 目标的深度 9 BFS 共 4,807 个状态，另外 48 个固定种子随机状态用 A* Manhattan 求精确最优解长，5,000 个深随机排列检查全部相邻边的一致性。深随机排列没有独立求精确距离，不能把它们计作完整 15-Puzzle 可采纳性穷举。

测试总计 7,022,745 项检查、549,127 个 BFS 状态、1,466,528 条 BFS 状态出边和 15,043 条深随机边通过，详见 [独立测试记录](../results/optimization-20261106-20261106T115705068678Z/tests/optimization-final/correctness.json)。`PuzzleStage2Test` 也新增标准目标全空间一致性检查。测试失败时保存上下文、棋盘编码、h、精确距离或后继，不跳过反例。

## TT、Zobrist 与阈值

`IdAStar` 的 TT 保存 `State -> best g`。相同状态的较大或相等 g 被剪枝，较小 g 更新后继续搜索。ZOBRIST 先用 64 位键找到桶，再逐项 `State.equals()`，相同哈希不等于相同棋盘。两者在达到容量后停止接纳新状态，仍允许更新已有状态的更小 g；不把未记录状态当作重复。每次 f 阈值迭代重新清空表，路径集合也重新建立。

Zobrist 给每个位置和取值分配固定种子的随机 64 位数，棋盘键为这些数的异或。一次交换可以异或移除旧的两个位置贡献、加入新的贡献，无须重新遍历全部格子。这是快速取桶键，并不消除碰撞；项目保留完整棋盘比较。原始方法见 [Zobrist 的技术报告](https://research.cs.wisc.edu/techreports/1970/TR88.pdf)。Java TT 同样依赖 `equals`，不是只比较 32 位 `hashCode`。

生产代码先处理 `f > bound`，再判目标、再查 TT。因而超界结点会返回实际 f，不会先被表剪掉。表内支配剪枝返回无新候选值，而被保留的较低 g 搜索负责提供界限和延续；不能把该值改成 0，不能复用上一轮表，也不能把“见过某状态”当作永久 Closed。测试直接检查较大/相等/较小 g、容量 1 时的更新和不接纳行为，并用 300 个带环随机有向图与独立反向最短距离比较；所有状态强制同 Zobrist 和同 Java 哈希，测试包含可采纳但不一致的 h、容量 0/1/3/100、连续重复搜索以及阈值不跳过最优解代价。有限测试不构成对任意图所有实现变体的普遍证明。

新增计数器只观察已有搜索分支：反向过滤、实际子状态/子结点构造调用、全量/增量启发调用、路径集合峰值。未更改 TT 剪枝规则或启发函数公式。所有正式矩阵共享冻结的 Java 源码清单。

`incremental_heuristic_evaluations` 计的是 `IncrementalPredictor.successorHeuristics` 接口调用。Manhattan/Misplaced 在该接口中更新单枚将牌的贡献，LC 分支仍重新计算整个 Manhattan 与冲突值，因此不能把 LC 的接口调用次数当作 O(1) 增量计算次数。完整边测试核对接口结果与全量结果相等。

## PDB、0-1 BFS 与成本

加性 PDB 对互不重叠的非空将牌组分别建立抽象距离表。移动本组将牌的成本为 1，移动其他将牌的成本为 0；每次真实移动恰好只由一组承担，因而可以相加得到下界。`PatternTable` 使用 0-1 BFS：改进的 0 成本边放双端队列头，1 成本边放尾；不能直接用所有抽象边等价为 1 的普通 BFS 替代。理论依据见 [Felner、Hanan 与 Korf 的加性 PDB 论文](https://arxiv.org/abs/1107.0050)。项目既有抽象图测试验证表距，历史单点 BiBFS 不等于完整加性建表。

Hard 使用 555T。四启发比较中，3×3 使用 4-4，普通 4×4 使用 4-4-4-3，保持历史主比较的分组口径；不能把它们当作 555T 同一工作负载。建表和落盘、加载及校验来自 `PatternTable.preparationMs()`，逐表按实际 loaded 状态分列；现有接口为整数毫秒。`elapsed_ms` 只覆盖搜索（包括启发查询及同步记录器），`parent_ms` 从创建实际 JVM 前到退出/终止并回收，包含准备、搜索、回放与导出。两者差值不是纯 JVM 启动时间。

PDB 文件字节、表条目、构造次数、`-Xmx1024m` 及当前堆值均不代表峰值堆内存。查询次数也不等于查询时间；独立 CPU 采样只作诊断，不混入正式时间中位数。

## 复现

从已经提交的仓库版本启动完整隔离流程（Python需要matplotlib，实际解释器路径可用 `-Python` 指定）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/run_optimization.ps1 -Python C:/ProgramData/anaconda3/envs/hsi_env/python.exe
```

脚本在仓库内创建新的忽略工作树，使用已提交HEAD；原工作区不会被修改，也不自动提交新数据。下列分步命令只在这种**直接嵌套于原仓库内的独立工作树**中执行，`init` 会读取父目录原工作区建立保护清单：

```powershell
python tools/optimization_suite.py init
# 将上一步打印的新目录作为 <suite>，不会复用已有目录
python tools/optimization_suite.py prepare --suite <suite>
python tools/optimization_suite.py run --suite <suite>
python tools/optimization_diagnostics.py <suite>
python tools/analyze_optimization.py <suite>
python tools/verify_optimization.py <suite> --output <suite>/verification.json
python tests/test_optimization_tools.py
```

`init` 程序生成 UTC 时间戳。`prepare` 在不存在的构建目录编译、运行 9 套 Java 测试并冻结清单；`run` 为每组启动新 JVM，不在同 JVM 中预热。Hard 主矩阵使用预实验建立的本轮私有热缓存，比较前后校验 PDB 哈希；独立 BASIC 冷运行和四启发 PDB 每次使用不存在的新缓存。Hard 父端 60 秒、1024m 不变；普通对照 15 秒；首个冷建表预实验给 30 秒，其余预实验 15 秒。失败不会自动扩大预算或重跑，脚本拒绝覆盖已有计划和输出。

`tests/test_optimization_tools.py` 的路径拒绝测试使用本次已提交的 52 步路径作固定回归夹具；它检查错题、非法方向及失败耗时排除，和 Java 最优性测试互补。`tools/verify_project.py` 仍校验历史数据源；历史 source-manifest 与当前源码不同会明确展示为版本演进，不能据此改写旧清单。旧 DOCX/PDF 一致性只检查历史段落，明确标记的 Markdown 新实验补充由本轮独立验收负责。

## 实测结论与推荐

正式矩阵共 80 次，状态为 SOLVED:61, TIMEOUT:19；另保留首次启动器 TIMEOUT 预实验1次，以及15次独立诊断（12次普通题控制、3次JFR Hard尝试）。这些诊断不计入正式中位数。

JFR前两次在JVM初始化阶段FAIL：第一次录制参数解析失败，第二次无法创建沙箱临时录制目录，都没有进入搜索，原日志不改写。第三次经明确权限请求在沙箱外采样；它与正式矩阵执行条件不同，采样只描述这次诊断，不把它的耗时或样本比例当作沙箱中正式运行的精确结果。诊断编译首次也因沙箱类路径枚举失败，失败日志保留；同源码在沙箱外编译通过，12次普通控制仍在原沙箱环境运行。

每格3次新JVM，固定种子打乱顺序，使用本轮私有555T热缓存。快照控制复用正式运行器的计数序列化，反射调用会增加少量诊断开销；它只能描述普通题观察到的记录器差异，不能推算 Hard 的精确开销。fast 仍是多个机制的组合开关：立即反向移动在创建状态前过滤，其他路径环仍由 pathStates 排除，子结点逐个创建；三者不能各自分摊为独立加速比例。PDB 没有增量预测接口，这组不含 Manhattan 的增量距离收益。

独立 JFR Hard 诊断中，带 IDA* 搜索栈的 CPU 样本 2192 个，其中出现 PDB 栈 1224 个（55.84%）。PDB 是该诊断中的主要采样 CPU 热点。这不是精确墙钟时间占比，JIT 内联和采样存在偏差；JFR 启动开销与该次耗时不进入正式对照。原始二进制留在忽略的 generated/，仓库保留栈计数摘要。

PDB 是否值得应分别回答：一次性普通题，直接比较上表冷父端；多次相同目标可复用时，只计一次建表再按次加载；Hard 冷运行是否达标单独看实际状态。没有测多个目标和不同难度分布的摊销盈亏点，不给普适的“运行几次必然回本”。

就本次两个普通题的一次性冷启动而言，PDB 不划算：父端中位约8.7—11.4秒，Manhattan约0.26—1.14秒。普通4×4的A*使用LC，搜索中位由869.637降至671.068毫秒，扩展由339,410降至184,819；IDA*虽然也少扩展，却由275.604升至639.747毫秒。LC额外计算的代价必须和减少的搜索一起评价，本题不建议用它替换IDA*的Manhattan。

fast有可测的组合收益：普通题无快照控制中位从107.775降至82.074毫秒；Hard第3组完整配对从51.485降至37.509秒。该组生成事件减少48,759,757，恰好等于被提前过滤的反向移动数；子状态、子结点和查询减少还包括提前路径检查、逐个生成及未访问兄弟等影响。不能把整个时间差全部归因于一个子优化，也不能把只有1组双成功的Hard结果宣称为稳定加速倍数。

本轮仍只有固定实例各3次，给出原始点、成功率、成功中位数和观察范围，不声称统计显著性。历史同题 CSV、Hard 冷/热基线仍原路径保留；历史快慢差异包含运行环境负载与JIT/GC等未隔离因素，不能把新旧时长差当作优化净收益。
